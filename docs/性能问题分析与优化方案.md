# EE5110 事件相机模拟器：内存故障分析与性能优化

## 1. 问题背景

本项目使用普通高帧率视频模拟事件相机输出。程序将每一帧转换为对数亮度，并在单个像素的亮度变化跨过对比度阈值时生成事件 `(x, y, t, p)`。其中 `x, y` 为像素坐标，`t` 为事件时间，`p` 为事件极性。当前模型采用相邻帧之间的线性插值，并假设传感器没有阈值失配、热像素、漏事件和其他噪声。

在处理低帧率、全高清驾驶视频时，旧版本程序发生了 NumPy 内存分配错误。本次工作首先分析错误原因，再从处理流程和事件生成内核两个层面进行优化。

## 2. 对课程要求的核对

根据 `EE5110_6110_JiangRui_Lec01.pdf` 第 6 页和第 92–96 页，项目要求可以整理为：

| 项目 | 课件要求 | 本项目处理方式 |
| --- | --- | --- |
| 输入 | 高帧率图像；I/O 页明确写为一个视频片段 | 直接读取 `input/` 中的视频 |
| 模拟参数 | 触发阈值、时间戳分辨率等 | 正负阈值、epsilon、1 微秒时间戳分辨率 |
| 时间估计 | 从离散帧插值到连续时间 | 使用相邻帧之间的线性插值 |
| 噪声 | 需要说明噪声假设 | 当前采用理想无噪声模型 |
| 主要输出 | 完整事件列表 | HDF5 中保存 `x/y/t/p` 四个字段 |
| 可视化 | 在输入视频上叠加事件帧 | 输出红色 ON、蓝色 OFF 的叠加视频 |
| 累积时间 | 支持自定义累积时间 | 由 `ACCUMULATION_TIME` 配置 |
| 其他考虑 | 多 FPS、运行效率、界面、数据压缩 | 自动读取固定 FPS、显示进度、流式无损压缩 |

课件中的 “high frame-rate images” 指视频中的连续高帧率图像，并不意味着程序必须把图片序列作为主要输入。第 96 页明确提出输入可以是一个视频片段，因此当前的视频输入方式符合要求。

课件第 82–87 页还区分了原始事件列表、事件帧和事件张量。事件帧便于可视化，但会丢失事件的精确时间和重复触发信息，所以叠加视频不能替代完整事件列表。

## 3. 故障复现

输入视频 `driving.mp4` 的基本信息为：

| 属性 | 数值 |
| --- | ---: |
| FPS | 30 |
| 分辨率 | 1920 × 1080 |
| 总帧数 | 1230 |
| 视频时长 | 约 41 秒 |

旧版本运行到第 850 帧时已经累计生成 `781,286,877` 个事件，随后出现错误：

```text
numpy._core._exceptions._ArrayMemoryError:
Unable to allocate 15.8 MiB for an array
with shape (1080, 1920) and data type float64
```

错误发生在参考亮度更新：

```python
self.reference_log += positive_counts * self.threshold_pos
```

表面上看，程序只是无法申请一块 15.8 MiB 的数组；实际上，在这一行执行前，数亿个历史事件已经占用了绝大部分内存。15.8 MiB 的临时数组只是内存耗尽后的最后一次失败。

## 4. 内存占用的定量分析

旧版本为每个事件保存四个独立 NumPy 字段：

| 字段 | 类型 | 每个事件占用 |
| --- | --- | ---: |
| `x` | `int32` | 4 字节 |
| `y` | `int32` | 4 字节 |
| `t` | `float64` | 8 字节 |
| `p` | `int8` | 1 字节 |
| 合计 |  | 17 字节 |

因此，第 850 帧时仅事件字段的理论下限为：

```text
781,286,877 × 17 bytes
= 13,281,876,909 bytes
≈ 12.37 GiB
```

这个结果还不包含：

- Python 列表和每帧事件字典；
- 正负事件的中间批次；
- `np.concatenate()` 产生的完整副本；
- `np.argsort()` 的排序索引；
- 按索引重排 `x/y/t/p` 时产生的副本；
- 当前视频帧、对数亮度、阈值计数和其他全帧数组；
- NPZ 压缩期间的缓存。

如果简单按照第 850 帧的平均事件量外推到 1230 帧，完整视频可能产生约 11.3 亿个事件，对应约 17.9 GiB 的未压缩事件字段。该外推只用于说明数据规模，实际事件速率会随场景内容变化。

作为对照，`source_240fps_640x360.mp4` 共 419 帧，已经生成约 6454 万个事件。即使分辨率和时长较小，未压缩事件字段仍约为 1.02 GiB。这说明事件文件大小主要由事件数量决定，而不是由原 MP4 文件大小决定。

## 5. 原处理流程的主要瓶颈

### 5.1 所有事件长期驻留内存

旧流程把每一帧生成的事件加入 `event_batches`，直到视频全部处理完成后才拼接和保存：

```text
逐帧生成 → 保存所有批次到内存 → 全量拼接 → NPZ 压缩 → 再次读取视频可视化
```

因此峰值内存会随视频累计事件数近似线性增长。即使每帧计算本身没有问题，只要视频足够长，最终仍会耗尽内存。

### 5.2 逐阈值层级反复扫描整幅图像

旧事件内核先计算每个像素跨过的阈值次数，再执行：

```python
for level in range(1, counts.max() + 1):
    y, x = np.nonzero(counts >= level)
```

如果部分像素在相邻帧间跨过多个阈值，程序会针对每个 `level` 重新检查全部像素。全高清图像每次扫描约 207 万个像素，重复扫描会显著增加 CPU 时间和内存带宽压力。

### 5.3 每帧事件排序和复制

正负事件生成后需要按插值时间排序。排序索引通常使用 `int64`，每个事件还需额外占用 8 字节；使用排序索引重排四个字段时又会产生新的数组。

事件流需要保持时间顺序，因此当前仍保留每帧一次稳定排序，但避免了全视频结束后的第二次大规模拼接。

### 5.4 NPZ 无法方便地追加

`np.savez_compressed()` 适合一次保存已经存在于内存中的数组，不适合持续追加数亿个事件。为了输出单个 NPZ，旧版本只能先在内存中收集完整事件。

### 5.5 可视化重复读取视频

旧版本生成事件后重新打开输入视频，再根据完整事件数组制作叠加视频。这增加了一次视频解码，也要求完整事件数组在可视化阶段继续保留。

## 6. 优化后的处理流程

新流程为：

```text
读取一帧
  ↓
生成并排序当前帧事件
  ├─ 立即追加到 HDF5
  ├─ 收集最多 100000 个 CSV 样例
  ├─ 更新快照时间窗口
  └─ 使用近期事件写入当前叠加帧
  ↓
释放不再需要的事件批次并读取下一帧
```

此时内存主要取决于当前视频帧、全帧状态数组、当前一帧产生的事件、可视化累积窗口内的近期事件和 HDF5 分块缓存。内存不再与视频的累计事件总数成正比。

流式处理不能减少事件文件本身的磁盘空间，也不能保证单帧事件批次永远很小，但可以消除最主要的全视频内存增长问题。

## 7. 已采用的优化

### 7.1 流式 HDF5 事件文件

完整事件列表改为 `events.h5`，包含四个一维、可扩展的数据集：

```text
/x  int32
/y  int32
/t  float64, seconds
/p  int8
```

每个数据集使用约 262144 个事件的分块，并启用 shuffle 和 LZF 无损压缩。LZF 的压缩率可能低于高等级 gzip，但速度较快，更适合边计算边写入的处理流程。

HDF5 文件还记录阈值、时间戳分辨率、模型类型、源视频、事件数和完成状态。读取时可以按块访问，不需要一次加载完整文件。

### 7.2 单遍视频处理

事件计算、HDF5 写入、快照和叠加视频在同一次输入视频读取中完成。叠加视频只保存累积时间窗口内的事件批次。例如累积时间为 0.01 秒、输入为 240 FPS 时，通常只需保留最近约 2–3 帧产生的事件。

### 7.3 活动像素向量化展开

新事件内核只找出 `counts > 0` 的活动像素，然后根据每个活动像素的触发次数生成 `[1, 2, ..., count]` 阈值序列。这样避免按阈值层级重复扫描整幅图像。

这种实现与逐像素模型在数学上等价，仍然为跨过的每一个阈值生成一个事件，也仍然使用线性插值估计事件时间。

### 7.4 1 微秒时间戳量化

线性插值得到的连续时间先进行稳定排序，再量化到 `TIMESTAMP_RESOLUTION = 1e-6 seconds`。这与课件中“时间戳分辨率”参数相对应，也能避免量化产生的同时间戳改变原有先后顺序。

### 7.5 避免全帧 float64 更新临时量

对比度计数为 `int32`，阈值为 Python 浮点数时，旧表达式会产生整幅 `float64` 乘法结果。直接把运算改成 `float32` 会造成极少量阈值边界事件发生变化，因此新实现保留原有数值语义，但每次只更新 128 行。全高清图像的临时量由约 15.8 MiB 降为约 1.88 MiB，同时保持原事件数量。

### 7.6 安全输出和运行统计

程序先写入带有 `partial` 标记的文件，全部完成并检查字段长度后再替换正式结果。运行时显示已处理帧数、累计事件数、当前处理速度、HDF5 文件大小，以及外推的事件数量和空间。

元数据分别记录事件生成、HDF5 写入、可视化和最终收尾耗时，以便判断下一步应优化哪一部分。

## 8. 关于低帧率输入

课件使用 960 FPS 作为高帧率示例，但第 96 页也提出是否支持多种 FPS。项目因此不会拒绝 30 FPS 视频，不过会显示提示。

低 FPS 并不必然使整段视频产生更多事件，但会带来以下问题：

- 相邻帧之间时间更长，像素变化更大；
- 单帧可能一次跨过更多阈值，形成很大的事件批次；
- 线性亮度插值难以描述帧间真实的非线性运动；
- 运动模糊和遮挡可能降低模拟真实性。

因此，`source_240fps_640x360.mp4` 更适合展示模拟效果和验证算法；`driving.mp4` 更适合作为内存和吞吐量压力测试。

### 9.1 全高清驾驶视频压力测试

优化版本还完整处理了原先发生内存错误的 `driving.mp4`：

| 指标 | 实测结果 |
| --- | ---: |
| 视频 | 1920 × 1080，30 FPS，1230 帧 |
| 第 850 帧累计事件数 | 781,286,877 |
| 最终事件总数 | 1,108,350,313 |
| 总时间 | 341.40 s |
| 事件生成时间 | 272.22 s |
| HDF5 写入时间 | 34.05 s |
| 可视化时间 | 29.02 s |
| 平均处理速度 | 3.60 frames/s |
| 事件吞吐量 | 3,246,505 events/s |
| HDF5 大小 | 4,753,712,655 bytes，约 4.43 GiB |
| 运行结果 | 完成全部 1230 帧 |

新程序在第 850 帧得到与旧日志相同的事件数，但没有发生内存错误，并继续完成剩余 380 帧。最终事件字段若不压缩，理论大小约为 `1,108,350,313 × 17 bytes = 17.55 GiB`；流式 LZF HDF5 为约 4.43 GiB。

这次测试验证了内存故障的主要原因是保存全部历史事件，而不是第 850 帧本身的计算。需要注意，本次没有使用进程级内存监控工具记录峰值 RAM，因此只将“完整运行且越过原崩溃点”作为稳定性证据，不填写未经测量的峰值内存数值。

## 10. 后续优化方向

1. 根据 `metadata.json` 判断主要瓶颈是事件生成、排序、HDF5 压缩还是 MP4 编码。
2. 如果单帧事件也达到数千万级，把一帧事件进一步拆成有序子块并归并写入。
3. 研究直接生成有序事件或归并多个有序阈值流，减少完整 `argsort()` 的成本。
4. 尝试课件第 87–90 页提出的时间戳差分、坐标差分或事件分组，并与通用 LZF 比较。
5. 在核心结果稳定后，再单独研究阈值失配、热像素、漏事件和强度相关噪声。
6. 只有分析确认事件生成计算占主导时再考虑 C++ 或 GPU。GPU 不能消除十亿级事件的存储和输出开销。

## 11. 结论

本次故障的根本原因不是某一块 15.8 MiB 数组，而是旧流程长期保存约 7.81 亿个事件，导致事件数据、排序副本和图像临时量共同耗尽内存。优化后的方案将事件改为流式无损写入，并在一次视频读取中完成可视化，使内存占用从“随累计事件总数增长”变为“主要受单帧事件量和可视化窗口影响”。

同时，向量化活动像素展开减少了重复整图扫描，1 微秒时间戳分辨率和无噪声假设也使模型描述更符合课件提出的设计要素。最终性能提升必须通过统一输入和参数的实测结果给出，而不能仅根据实现方式推测。
